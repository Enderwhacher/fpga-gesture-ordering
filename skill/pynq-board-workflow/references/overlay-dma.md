# Overlay、寄存器与 DMA

## Overlay 分两步

先检查 bit 和同名 hwh 是否来自同一次构建，核对器件、IP、接口和驱动。SHA 只能证明文件身份，不能单独证明两者匹配。

在具备对应 PYNQ 环境时，可用 `Overlay(bit_path, download=False)` 解析描述，再检查 `ip_dict`。这不等于实际硬件已加载，不要据此访问 IP 寄存器。确认当前资源可切换后再显式下载；默认构造可能直接下载硬件，不能用于无意的探测。

完整 bitstream 通常替换当前 PL 设计。base 视频和另一个完整加速 bit 不能靠先后加载实现同时驻留；需合并设计，或改为外部显示。部分重配置属于另一个经过设计的流程，不能假定具备。

## 写清接口契约

核对输入/输出 shape、dtype、内存布局、字节序、字节数、AXIS 数据宽度、TLAST/TKEEP、控制协议、地址宽度、DMA 模式和长度上限。DMA 可传长度来自当前 IP 参数/驱动，不硬编码某演示值。

IP、DMA、互连各时钟域与 reset 极性都要核对。设计中的名义时钟、系统实际配置及驱动容许范围应一致；不要为跳过检查把合理范围放宽。AXI 基地址从当前 HWH 解析，禁止套用其他板的地址。

## 数据与事务

使用 `pynq.allocate` 分配供 PL 访问的 buffer，普通 NumPy 数组不能直接视为 DMA 物理连续内存。不要在活跃 DMA 期间释放或改写其 buffer；返回结果需明确是独立副本还是暂借视图。

根据所用驱动确认缓存维护责任：PS 写后在设备读前同步，设备写后在 PS 读前同步；驱动已做的动作不重复增加到性能路径。相应 Buffer API 包括 `flush`/`invalidate`，一致性以实际平台为准。

对有输出的流式核，常用安排为先挂接收，再按核控制协议启动与发送，等待双方完成。具体顺序必须匹配设计，不能把 loopback 示例照搬到自定义命令核。发送结束不等于输出计算完成；S2MM 需正确的末拍信号及长度契约。

标准 `.wait()` 是否有时间限制以本机驱动为准，不假定支持 `timeout=`。生产调试用已有驱动的有界状态检查或明确恢复策略；对阻塞调用套一个 Python 线程超时不会取消硬件事务。

最小验证采用已知输入及 CPU 黄金输出，检查形状、有限值、绝对/相对误差，再检查完整应用语义。参数驻留型 IP 还需验证首次 LOAD、重复 RUN、重载、Overlay 重载后重新初始化。
